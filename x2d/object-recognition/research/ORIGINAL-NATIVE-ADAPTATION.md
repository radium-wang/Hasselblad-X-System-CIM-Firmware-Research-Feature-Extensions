# 二代原厂识别／追踪模块适配：2026-09-26 离线结果

适用：X2D 4.2.0 ← X2D II 1.3.16.2。以下均为本地固件 ELF 静态分析，不是机内运行结果。

用户要求保留二代原厂算法，适配第一代接口并排除 LiDAR。此前公开 YOLO CPU 检测器、截图轮询和自写 NCC 追踪路线已退役，不能作为此目标的实现。用户已确认恢复后额外调试菜单消失；本轮没有连接、上传、修改或重启相机。

## 1. 已定位真正需要移植的原厂实现

二代 `bin/dji_ml` 中存在：

| 原厂入口 | ELF 虚拟地址 | 对应边界 |
| --- | --- | --- |
| `CreateDetectionSubGraph` | `0x103144` | 检测子图 |
| `CreateTrackingSubGraph` | `0x1685b8` | 追踪子图 |
| `CreateReidSubGraph` | `0x10b6e8` | 重识别子图 |
| `TrackingSubGraph::ReceiveFrameEventTrigger` | `0x16c2dc` | 帧事件入口 |
| `ArbitraryTrackingSubGraph::ReceiveFrameEventTrigger` | `0x15fef4` | 任意目标追踪帧事件 |
| `FrameManager::PushImage` | `0x136bd4` | 原生图像输入 |

二代 `libcnntk_cbb.so` 含 `CNNTKInit`、`CNNTKSingleTrackerUpdate`、`CNNTKTemplateSelect`、`CNNTKTemplateUpdate`，及 SiamRPN / SiamRPNPP / SOT 实现。存在某个实现不等于已证实量产配置实际选择它。

原厂配置包括 `tracking_sub_graph.prototxt.eng.enc`、`arbitrary_tracking_sub_graph.prototxt.eng.enc`、`cnntk.json.eng.enc`、`afc_tracking.json.eng.enc`、`dynamic_roi.json.eng.enc`、`yolov8.json.eng.enc`。原厂还提供注册解密回调的入口。应优先保留原厂解析路径，不把加密模型转交此前的 OpenCV CPU 替代程序。

这些入口提供了原生帧驱动和独立追踪链路的静态证据；不是二代实际帧率、第一代性能或可加载性的证明。尚未证明所有选定运行路径均不依赖 LiDAR。

## 2. 从“找齐库名”推进到版本化符号

`tools/audit_native_bundle.py` 新增 provider-specific 强引用符号版本检查、原始文件哈希清单，以及 `--source-library` 离线对照选项。

| 候选组合 | 二代库数 | 未版本化缺口 | 版本化强引用检查 | 上机状态 |
| --- | ---: | --- | --- | --- |
| 保留一代 `libdsp_frwk.so` | 31 | 无 | 6753 项中 2 项失败 | 未批准 |
| 选入二代 `libdsp_frwk.so` | 32 | 无 | 6779 项，无缺口 | 未批准 |

两个失败消费者为二代 `dji_ml` 与 `libnn_framework.so`，都要求 `__emutls_get_address@libdsp_frwk_v_lz`。第一代 DSP 库没有此导出。仅从别的库找到同名符号会漏掉这一约束。

二代 `libperf_trace.so` 和 `libduml_fastrtps.so` 也有该线程局部存储辅助函数，但版本名不同。DSP 与 perf-trace 的辅助函数均为 336 字节，反汇编控制流高度相似；**不能因此直接认定可替换**，还需验证控制对象布局、TLS 索引／线程析构一致性、加载范围和实际绑定。当前没有改写 ELF 版本表，也没有用取消版本检查掩盖缺口。

32 库组合只是离线符号门禁通过：没有模拟 Android 链接器，没有执行构造函数，没有证明对象布局、资源所有权或硬件协议兼容；也未证明组合最小。

## 3. 可复用第一代加速器接口的积极证据

二代用户态封装与两代内核 ioctl 分支的命令和显式复制大小一致：

| 接口 | ioctl | 实际内核复制大小 |
| --- | --- | ---: |
| CNN 分段数 | `0x40084300` | 8 字节 |
| CNN 网络信息 | `0x40084301` | 56 字节 |
| CNN 等待 | `0xc0084302` | 416 字节 |
| VCR acquire / release | `0x40085600` / `0x40085601` | 各 12 字节 |
| VCR run task | `0x40085602` | 152 字节 |
| VCR wait | `0x40085603` | 12 字节 |
| VCR cost count | `0x80085604` | 4 字节输出 |

核对位置：一代／二代 `cnn_ioctl` 分别 `0x5d8`／`0xbc0`；`vcr_ioctl` 分别 `0x840`／`0xcdc`。二代用户库 CNN 封装为 `0x1650`、`0x16e0`、`0x1780`；VCR 为 `0x2aa0`、`0x2b10`、`0x2b80`、`0x2be0`、`0x2c50`。

不要把 ioctl 编码的 size=8 当作真实结构大小；此处大小来自 copy 操作和封装实际取用范围。字段含义、模型指令、DMA／缓存同步、并发调度仍未逐项闭合。

两代内核分别为 `4.9.130-rt125-g34abb7a5` 和 `5.4.123-rt59-g5b4774899a19-ab316`。禁止将二代 `.ko` 直接塞入第一代；用户态适配方向应保留第一代内核。

## 4. DSP：版本相同，但发现通信差异

两代握手函数确实比较 `0x00020301` 的 DSP framework 版本和 `0x01050000` 的 ICC 版本，不仅是错误字符串相同：

- 一代比较位置：`0x5f88–0x5fa8`。
- 二代比较位置：`0x7a4c–0x7a6c`。

但同一握手回调对 `ss_icc_send_sync` 的调用，第一代第二参数为 `0x10`，二代为 `0x0f`，超时参数均为 `0x190`。二代 `ss_icc_send_sync_nowait` 将该第二参数用于命令索引与消息状态；它不是可以忽略的库地址差异。还不能凭此一个调用推导完整编号映射，也不能把所有消息机械加一。

因此优先研究“保留一代 DSP 通信库，仅适配二代用户态 ABI”。若选择二代 DSP 用户库，必须先逐项核对通信命令和共享数据布局；符号零缺口不能授权直接启动。

## 5. 当前具体适配边界与未完成项

1. 算法层：保留二代原厂检测／追踪／重识别模块及原厂模型；不编写替代识别或追踪算法。
2. 硬件层：保留第一代内核和 DSP 固件；核对 CNN/VCR 字段、DSP ABI 及模型运行路径。
3. 输入层：适配一代原生帧描述符、共享内存与生命周期，不走 GUI 截图。
4. 输出层：对接目标 ID、矩形、丢失状态及第一代 AF 合法坐标／时序；不能仅画框或把对象伪装成人脸。
5. UI 层：复用二代对象指示框逻辑，适配第一代数据接口；未合焦时不得显示表示合焦成功的绿框。
6. LiDAR：追踪每个实际调用／配置依赖，证明绕开雷达仍可完成模型、帧和 AF 链路；不能全局删除相关字符串冒充适配。

尚未产生可部署的原厂移植包。下一项最小验证是补齐保留一代 DSP 的 ABI／TLS 绑定证据，再评估原厂模型及原生帧路径；不会以“完整移植”为名覆盖 `camera-service`、DSP 固件或内核驱动。

## 后续进展：原厂 ELF 导入适配副本与取景帧结构

### 已实现的离线适配，不是安装包

`d474ccfc8d0ba6b1f9b95021b6ec35ab655ace935e53029e428adb0663d100f2`。

两个消费者已经直接依赖该库。适配仅把它们的 `__emutls_get_address` 导入显式绑定至该库已有的 `libduml_fastrtps_v_lz` 版本，**没有取消版本检查、没有改检测／追踪算法代码，也没有替换第一代 DSP**。

### 原生帧入口：找到具体结构差异

二代既有 DDS 帧订阅回调（`0x138afc`），也有 DSH 回调；不能假设必须通过 GUI 截图输入。一代日志交叉引用定位到 `vpfFrameRecvCallback`，二代定位到 `DshRecvFrameCallBack`。通过同义日志参数的读取指令确认下列偏移，均相对于回调第三个参数指向的帧结构：

| 字段（按原厂日志语义） | 一代 4.2.0 | 二代 1.3.16.2 |
| --- | ---: | ---: |
| 像素格式 | `0x134` | `0x134` |
| 时间戳（64 位） | `0x13c` | `0x13c` |
| 宽／高 | `0x144` / `0x148` | `0x144` / `0x148` |
| 第一平面 bytes/line | `0x14c` | `0x14c` |
| plane_count | `0x18c` | `0x1bc` |
| frame_id | `0x190` | `0x1c0` |

一代读字段及日志位置为 `0xbcb84–0xbcbe8`，二代为 `0x134aec–0x134b50`。输入哈希见上表。两代回调都取 `frame + 0x10c` 作为内部图像描述起点，但后续内存句柄获取路径不同。

这说明不能把一代帧指针直接传给二代接收器：二代会从不同位置取 plane_count/frame_id，并在该 DSH 路径另访问 `frame + 0x43c`。**不能仅补 0x30 字节或复制几个字段就认定完成适配**。需继续核对每个被读取字段、共享内存句柄、回调上下文及引用／释放时机；目前尚未实现完整帧转换器，未注册回调。

### 后续：帧生命周期与完整记录边界（静态验证）

新增 [audit_original_frame_contract.py](../tools/audit_original_frame_contract.py)；仅使用 Capstone 反汇编，不使用已在本机崩溃的 Unicorn。固定哈希的两代原厂 `dji_ml` 共 29 个关键指令断言及 PLT 导入核对通过。提供两代固件根目录时，模块 23 项离线测试全部通过。没有连接或改动相机。

| 适配点 | 一代原厂证据 | 二代原厂证据／要求 |
| --- | --- | --- |
| 同名 DSH 通道 1/2/3 回调编号 | `0/1/2`，`0xbd51c` 等 | `1/2/3`，`0x113a88` 等；不能据此直接给所有通道加一，实际图像来源仍须核对 |
| 帧描述符存储 | `0xbc588` 设 memcpy 大小 `0x218`，单个池项跨度 `0x258` | 原厂转换函数只生成 `0x68` 字节核心，但 `PushImage` 与 `PushImageWithDshInfo` 都 memcpy `0x84` 字节 |
| 原始帧所有权 | `0xbc5f4` 保存 owner/frame 两指针；过期清理 `0xbc754–0xbc758` 将其交给 `duss_dsh_data_release` | 不能将一代池内指针交给二代异步算法后任由一代清理 |
| 查询帧 | `0xbc790–0xbc8a4` 在锁内查找／复制描述符并返回池指针；此路径未见新引用获取 | 复制描述符不等于复制像素，也不等于取得独立帧租约 |
| 释放注册 | 必须沿原始 owner/释放协议适配 | `ShareFrameFreeRegister` 在本版本仅为 `mov w0, wzr; ret`，成功返回不能证明注册生效 |

一代过期扫描每通道检查 30 个池项，比较时间戳加 `0x249f0`（150000）与原厂时钟。此处只确认数值，不在时钟单位核实前把它写作毫秒；也没有改大超时或停掉回收来强占帧。

二代完整 `0x84` 记录的尾部不是任意填充：回调先清零整个记录，再由 `0x11338c` 从 `frame + 0x43c` 的相机附加信息提取字段，写入记录 `+0x68` 开始的区域，随后写通道字节。已确认的原厂字节规则：

- 完整记录 `+0x68`：回调转换后的通道编号低 8 位。
- `+0x69`：附加信息 `+3` 的 32 位值右移 28 后的低 8 位。
- `+0x6a`：附加信息 `+0x64` 的 32 位值乘 `0x51eb851f` 后右移 37 的低 8 位。
- `+0x6c..+0x7b`：附加信息 `+7` 的 16 字节原样复制。
- `+0x7c..+0x83`：附加信息 `+0x2f` 的 8 字节原样复制。

尚未确认这些字段在一代帧中的语义对应，不以全零填充冒充完整适配。`emulate_original_frame_adapter.py` 已增加独立尺寸门禁，明确拒绝将 `0x68` 核心当成完整记录；该门禁尚未接到任何实机调用，也不保证元数据语义或帧租约有效。

复现关键指令核对（从仓库根目录，无设备访问；另需 `capstone`、`pyelftools`）：

```sh
python3 -B x2d/object-recognition/tools/audit_original_frame_contract.py \
  --target-dji-ml /path/to/x2d-system-root/bin/dji_ml \
  --source-dji-ml /path/to/x2d2-system-root/bin/dji_ml
```

当前实现路线收敛为：保留二代原厂检测／追踪与一代硬件运行栈，在**原生帧入口**适配描述符、附加元数据、真实所有权和通道映射。下一项未闭合的是一代附加信息与独立持有／释放机制；不能先接 AF 再靠原厂参数覆盖来补救悬空帧或越界读取。

### 后续：保留一代通信层的 23 库组合与原生适配组件

静态分析发现不能只拦截 `dji_ml` 的上层描述符：`libduml_frwk.so` 的 `duss_dsh_mb_recv_process` 自身也有输入布局差异。

| 固件库 | SHA-256 | 接收路径复制证据 |
| --- | --- | --- |
| 一代 4.2.0 `libduml_frwk.so` | `bb110a2c94e6ed5b69a99048f3a30db5760754ec12ff4d1bdd7f6f431139b81d` | `0xf67b0` 设置长度 `0x490`；`0xf67bc` 调用 memcpy，写入 frame+0x80 |
| 二代 1.3.16.2 同名库 | `c37925331335c70e2624f987c670afe133ac18e4ae4e22ef47a1ca31b9a07906` | `0x14e018` 设置长度 `0x890`；`0x14e024` 调用 memcpy，写入 frame+0x80 |

以上是原厂接收路径实际复制范围，不是未经验证的完整线协议消息长度；直接给二代入口喂一代尺寸的存储区域存在越界读取风险。二代还在 `0x14de48` 调用 `duss_hal_mem_register_free_cb`，一代 `libduml_hal.so` 不导出该函数。原厂上层 `ShareFrameFreeRegister` 空实现与 HAL 中真正的内存释放通知不是同一接口。

已给依赖审计增加 `--retain-target-library`：锁定的一代库不能被贪心符号闭合自动替换；输入冲突拒绝，缺口保持显式失败。实际离线组合：

- 固定保留一代 `libduml_frwk.so`、`libduml_hal.so`、`libdsp_frwk.so`。

### 进一步收窄真实帧门禁：相同句柄槽与原厂导入路径

随后核对固定版本两代 `libduml_frwk.so` 的接收尾部：一代在 `0xf67ec–0xf67f4`、二代在 `0x14e054–0x14e05c`，都把输入消息 `+0x84` 的 64 位内存句柄写到接收帧 `+0x70`。二代 `dji_ml` 的 DSH 回调在 `0x134738–0x134744` 正是从帧 `+0x70` 取句柄，调用原厂导入助手。助手 `0x29571c` 使用 `duss_hal_mem_import`，`0x295760` 再查询大小；对应清理 `0x295698` 调用 `duss_hal_mem_free`。第一代自己的 `dji_ml` 也导入、释放原厂 HAL 内存，并在另一条虚拟地址转换路径调用 `duss_hal_mem_share`。这些是**可复用原厂句柄接口的静态证据**，不是已经建立真实帧租约的证明。

两代 `dji_ml` 还分别在 `0xa2044`／`0x293c4c` 以 `/dev/ion` 调用同名 `duss_hal_device_open`，随后调用 `duss_hal_device_start`；传入配置的本地零值初始化模式相同。保留一代 HAL 时，二代导入函数拿到的应是由保留的 HAL 创建的对象，而非把二代 HAL 私有对象直接交给一代函数。这个推论缩小了对象布局风险，但**不能代替目标库对句柄、缓存同步和引用计数的实机验证**。

还需区分“接收器”和“算法回调”的范围：一代接收器从 `frame+0x80` 复制 `0x490` 字节，覆盖到 `frame+0x510` 之前；二代回调的附加信息读取最远为 `frame+0x43c+0x64+4 = frame+0x4a4`，落在该范围内。因此，**保留一代接收器时，这几个已知读取点并非仅因复制长度不同而越界**。但不能把一代消息直接交给二代接收器，后者仍会复制 `0x890`；也不能从“地址落在范围内”推断该处字段语义相同。尤其没有证实一代释放原始 DSH owner 后，二代导入的句柄仍独立有效、其大小满足全部图像平面、以及模型异步消费完才释放。

`audit_original_frame_contract.py` 已固定断言上述装载、导入、大小查询和释放调用，离线 25 项测试通过。下一项高价值验证是**不接模型和 AF**的真实帧句柄租约试验：只读取得一个原生帧，在原厂导入／释放约束下核对句柄大小与释放后的有效性，再清理；若不能先做出独立且有界的租约，就不让二代追踪异步持有该帧。本轮未连接或改写相机。

后续隔离实机实验补记（X2D 4.2.0）：自建 4 KiB ION 缓冲区的第一轮因遗漏原厂初始化表的两个 ELF 重定位回调而未打开设备；修正后第二轮 `duss_hal_mem_import` 返回后，`duss_hal_mem_get_size` 失败，隔离进程退出码 138。测试没有接触真实帧、模型或 AF。每轮结束均核实临时文件删除、USB 回原厂模式、ADB 停止、服务运行、系统只读；用户确认取景、菜单、镜头正常。程序把物理地址作为导入参数；固定版 HAL 在 `0x278c8–0x27954` 根据句柄低十位分支，对齐物理地址进入编码值解包分支，区别于共享句柄导入。因此此实测不能当作原厂共享帧路径失败的证据。候选已隔离，真实帧租约门禁仍未通过，不能据此推进二代跟踪或 AF 实机加载。

进一步的修正版实机测试改用原厂 `duss_hal_mem_share` 生成句柄：同一隔离进程对 4 KiB 自建缓冲区执行共享、导入和大小查询全部通过，退出码 0；临时载荷删除、USB 回原厂、ADB 停止、相机服务运行、系统只读均已复核。此结果把一代原厂共享句柄 ABI 的**同进程导入**从待验证提升为实机通过，不包含原持有者释放后的寿命、跨进程所有权、真实帧、二代模型或 AF。旧物理地址候选仍属失败记录，不能重跑。

随后在第二轮隔离测试里核准两代原厂 `dji_ml` 的 `duss_hal_mem_free(handle)` ABI，成功执行 4 KiB 自建缓冲区的 `share → import → 释放原句柄 → 再查导入句柄大小 → 释放导入句柄`，退出码 0；临时文件、USB、ADB、服务和系统只读状态复核同上。这把**同一独立进程中原持有者释放后的导入句柄有效性**提升为实机通过，但仍不能外推到跨进程真实帧、原厂异步消费完成时序或二代模型和 AF。

第三轮隔离实机测试让全新执行的子进程先关闭继承的 ION 描述符，再重新打开自己的原厂 HAL，并通过测试管道接收共享句柄：接收端导入并核对大小后，发送端释放原句柄，接收端再次核对大小并释放导入句柄，输出 `ION_CROSS_PROCESS_PASS_NO_CAMERA_FRAME_OR_AF`、退出码 0。临时载荷删除、USB 原厂模式、ADB 停止、服务运行、系统只读复核通过。由此可确认一代原厂 HAL 对**自建 4 KiB 缓冲区**的跨进程共享句柄租约可用；真实取景帧元数据、帧消费者生命周期和二代原厂模型／AF 仍是独立门禁。

### 原厂 ML 帧发送端的长度差异

继续沿原厂 `camera/plugins/stream_filter/libdcam_x2d_ml_stream_filter.so` 的 `MLControl::sendFrame` 反查实际发送端，而非用 GUI 截图替代。固定 SHA-256 的一代 4.2.0 在 `0x8520/0x855c` 分别复制 `0x218` 字节输入帧结构和 `0x278` 字节发送区域；二代 1.3.16.2 在 `0xa28c/0xa2c4` 分别复制 `0x330` 和 `0x390` 字节。相同文件名与同名函数**并不代表同一帧 ABI**，差额都是 `0x118` 字节。双方复制前还会清零额外 `0x60` 字节区域，并初始化发送节点；因此仅凭长度不能断言二代尾部字段非零、有效，更不能把一代缺少的字段全零补齐当成原厂适配。

两代函数分别在 `0x85b4`／`0xa31c` 调用同名 `Dsh::send`，其后进入原厂 `duss_dsh_data_send`。此前“接收器复制范围覆盖二代回调读点”仅是边界事实；此次发送端证据进一步证明上游结构长度不同，尚需建立发送节点到接收帧的精确字段对应，并追查 `frame+0x43c` 等附加信息的实际来源。固定哈希和指令断言已加入 `audit_original_frame_contract.py`；提供两代固件根目录时 25 项离线测试全部通过。

继续沿**二代原厂这一条 ML 发送路径**核对清零与复制顺序，得到更窄的结论：`0xa278–0xa288` 先清零输入结构末尾 `0x60` 字节，`0xa298` 再只复制输入 `0x330` 字节，`0xa2a8` 清零发送节点 `0x910` 字节，`0xa300` 把两段连续的 `0x390` 字节复制到节点 `+0x10c`。因此在该发送节点中，`[+0x43c,+0x49c)` 确定为零，`[+0x49c,+0x910)` 也保留清零值。原厂二代通信层 `dsh_data_node_init` 在 `0x149ecc–0x149ed8` 清零共享节点 `0x910` 字节；`dsh_channel_shm_send` 在 `0x147828–0x147830` 依据节点 `+0x108` 的 `0x390` 长度，只从节点 `+0x80` 向共享节点同偏移复制 `0x390+0x90=0x420` 字节，覆盖终点为 `+0x4a0`。接收器从输入消息 `+0x94` 向接收帧 `+0x80` 复制 `0x890` 字节；该路径的句柄仍在接收帧 `+0x70`。第一代也有同构的清零／发送步骤，但尺寸是 `0x510`、`0x278+0x90=0x308`。

这使二代回调读取的 `frame+0x43c` 附近字段，在**已核对的发送节点内**落入明确清零区；先前不能把“额外 `0x118` 字节”直接当作含有效识别元数据。不过，尚未把共享节点如何成为接收消息的 `+0x94` 逐字节证实，也未排除其他生产者或传输阶段写入，因此不把这个条件结论升级为“一代可以无条件零填充二代所有元数据”。下一步应核实该传输映射和实际 ML 通道来源；真实帧租约、原厂模型加载与 AF 输出仍是分开的门禁。

机身上只读查询原厂日志，没有获得可用的 `vpfFrameRecvCallback` 帧元数据；看到的匹配项只是本次查询命令自身被诊断服务记录。原厂 `test_ec1706_frame_dump.sh` 虽可转储画面，但会开启调试框架、改相机拍摄设置并创建画面文件，而且转储像素并不等于取得 DSH 结构，所以本轮没有运行它。没有新的实机帧、模型或 AF 测试。

### 继续核对：封包映射成立，但完整附加记录仍差一个来源证明

进一步找到跨端事件封包函数：二代 `0x1482e8` 以 `node[+0x108]+0x110` 计算长度，`0x148368–0x148378` 把该长度的整个节点复制到消息 `+0x14`，随后交给 `duss_event_send`。第一代对应 `0xf7e68`、`0xf7ee8–0xf7ef8`。因此对于这条已定位的发送路径：节点 `+0x80` 对应消息 `+0x94`，节点 `+0x70` 对应消息 `+0x84`，恰与两代接收器读取相符；已不只是依据常量相似作猜测。

| --- | ---: | ---: |
| 事件中实际复制的节点字节数 | `0x388` | `0x4a0` |
| 回调的附加信息起点（二代布局） | 不适用 | `0x43c` |
| 回调附加信息的最大读取终点（不含） | 不适用 | `0x4a4` |

二代 `0x1133a4` 从附加信息 `+0x64` 读取四字节，正对应节点 `[+0x4a0,+0x4a4)`，**没有包含在上述事件的显式复制长度内**。发送栈及共享节点曾被清零，不等于接收方未传输区域也必然为零；需继续查明接收缓冲区初始化／复用行为或该机型真正选择的输入路径。这里不能据静态片段宣称二代量产固件存在实机越界故障，也不能把一代接收器的较大分配范围当作有效数据长度。本轮把这个差额加入审计输出和独立边界测试，未编写无条件填零的元数据适配器。

通道也有更具体的证据：二代 ML 插件在 `0xa81c` 创建发送通道 `101`；两代 `sendFrame` 均在节点 `+0x84` 写目的通道 `2`（一代 `0x8554/0x8568`，二代 `0xa2b0/0xa2c8`）。二代封包 `0x148364/0x148374` 读取目的项的通道值并写节点 `+0x78`。这两个通道角色不能混为同一编号；`Channel2Receive` 的一代／二代传入值为 `1/2`，而二代公共回调还经过内部映射表，不能把这个差异直接当作最终算法通道编号。

### 容器元数据对照与 -10 的相关原厂分支（纯离线）

本轮未连接相机，未读取设备启动区或受限区域。新增
[`audit_model_containers.py`](../tools/audit_model_containers.py)，只读取两代已提取固件
`model/ml` 下的模型及配套资源容器，验证长度／块边界、重算存储载荷的 SHA-256，
并固定核对二代原厂库中的相关错误分支。它不解密、不执行固件、不进行数字签名验证，
不输出原始头、签名、载荷、密钥材料或任意内部字符串。

字段名称参考公开 [IMaH 工具的结构定义](https://github.com/o-gs/dji-firmware-tools/blob/master/dji_imah_fwsig.py)，
偏移与原厂头字段读取交叉核对；未下载／执行该工具，未导入其密钥表或私钥。
不能将通用解析器的假设直接当作本机 TEE 的实际接受规则。

实际输入：X2D 4.2.0 的 23 个模型／配套资源容器，X2D II 1.3.16.2 的 22 个模型容器。
所有 45 个文件的以下字段相同，文件长度和块边界检查均通过：

| 字段 | 两代共同值 |
| --- | --- |
| `header_version` | 2 |
| 头及块描述总长度 | 224 字节 |
| 签名区长度 | 384 字节 |
| 算法字段原始值 | `0x00040003`（低 16 位为 3） |
| 验证材料标识 | `PRAK` |
| 加密材料标识 | `TBIE` |
| 块数量 | 1 |
| OS／架构／压缩／anti 单字节字段 | 均为 0 |

存储载荷 SHA-256 与各自头中摘要全部匹配，未发现此项完整性损坏。
但头中摘要匹配**不等于数字签名有效**；四字符标识相同也不等于设备内部选择了相同的
实际材料或版本。未将算法字段的高 16 位擅自解释为密钥版本，未修改任何头字段。

二代 `libfw_verify_util.so` 的 SHA-256 为
`696c145a40004c769009bd83128bbaef6f7fb67072b54123fb5194be51f93826`。
其 `plt_fw_verify_file_soft` 路径在 `0x1960` 调用 `sec_cipher_ecc_sha256_verify`，
`0x1968` 对非零返回跳往错误块，打印 ECDSA 验证失败信息后，在 `0x1b00` 返回 -10。
这是一条**相关错误约定的直接静态证据**，不是上次 TEE 内部路径的反汇编。
该软件路径在 `0x18e8/0x18ec` 要求算法低 16 位为 6，而本批模型为 3，
故不可把它当作这些模型的校验替代器。当前实际 TEE 返回 -10 的具体含义仍未被证明。

另在两代原厂 `bin/dji_fw_verify` 中找到验证／解密材料名称与版本选择参数的说明。
继续静态追踪 X2D 4.2.0 的实际参数传递，而非仅依赖帮助文字，得到：

- `bin/dji_fw_verify` SHA-256 为
  `003e2cd56b0e7b8826356f81bda640ca2cb71ad9fbdd16fff775f7e241186adf`。
  `0xbbc` 跳转表将 `-v/-V` 分别映射至 `0x9d4/0xa28`，
  `-d/-D` 分别映射至 `0x9e0/0x9c0`。两个版本全局变量初始值均为
  `0xffffffff`；这仅证明默认位模式，尚未证明安全服务如何解释它。
- 程序在 `0xad0` 调用 `dji_fw_verify_file`，以 `x5/w6` 传入验证材料名称／版本，
  `x7` 与第九个栈参数传入解密材料名称／版本。
- 一代 `libfw_util.so` 在 `0x174c` 保存 `w6`，在 `0x17bc/0x17c4`
  将这个**同一个版本值**分别放入 `w3/w5`，随后调用 `fw_util_verify_init_ext`。
  当前这条路径没有使用调用者提供的第九个版本参数。此为该版本代码的静态行为，
  不应把两个命令行版本选项当作已经验证可独立生效的功能，也未修改这一行为。
- 一代 `libfw_util_ca.so` 的 `fw_util_verify_init_ext` 确实复制两个材料名称，
  将两个版本值写入操作参数，并在 `0x1a60/0x1a88` 发送 TEE 命令 6。
  这证明参数不是只有说明文字；但它是分阶段文件校验初始化路径，
  **不是已经实测的内存模型加载命令 2**，不能假设会改变后者的默认选择。

未运行该文件校验程序：其路径可能创建／写入输出文件，失败时也有删除输出的行为，
不是可不加审查直接执行的只读诊断。没有猜测或遍历材料版本、没有导出密钥，
