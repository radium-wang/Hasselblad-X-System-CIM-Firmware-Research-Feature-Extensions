# X2D 菜单响应诊断与三轮优化试验

日期：2026-10-06 至 2026-10-07。范围：第一代 X2D 100C，固件 4.2.0 build24849，Android 9 / API 28、ARM64、Qt 6.4.1。原厂 camera-gui SHA256：`16391452abdc69de9e0807e065c0f4ab3f1ccb5fc288f6fc4e6f5cb3bdca12e0`。不推广到 X2D II 或其他固件。

## 当前结论

用户感觉菜单上下滑动与页面切换时，画面落后于仍在移动的手指。测量没有发现持续 CPU/GPU 饱和、显著低触摸报告频率或大量存储读写；连续操作的原厂 Weston 窗口平均为 57–58 FPS。**接近 60 FPS 仍可能有响应延迟，本次没有完成同一触摸事件到实际呈现的端到端测量，也没有确认唯一根因。**

三轮临时修改均未获得可区分、可重复的主观改善；最后恢复原厂进程与参数。同步拖动候选还出现原厂页面 ReferenceError，已撤回并禁止同一候选再次上机。它不是发布的性能优化。与之分开，[透明 Shimeji 宠物](../../shimeji-overlay/README.md)的直接拖动得到用户正面反馈，但不能据此说整机 UI 延迟已解决。

## 实机采样与口径

本轮原厂 GUI 已无宠物进程、状态通道或实验环境标记，GUI nice=-15。用户连续滑动约 20 秒；以下是本地记录的脱敏摘要，原始 getevent、proc、驱动日志及屏幕内容不随仓库提供。

| 观测 | 结果 | 能说明什么 |
| --- | --- | --- |
| 触摸 EV_SYN/SYN_REPORT | 2371 个；首尾 19.950 秒；相邻报告中位 6.952 ms、95 分位 13.891 ms | 短间隔通常约 144 Hz；不是应用或显示延迟 |
| 长触摸间隔 | 31 个大于 40 ms | 含静止/抬手的可能，不能直接认定丢触摸 |
| GUI CPU | 六个约 3.1 秒窗口，单核的 34.6–37.7%，按 USER_HZ=100 | 平均负载未满；不排除短时主线程阻塞 |
| GPU | 利用率 4–5%，驱动和固件状态正常，错误计数 0 | 平均负载低，不直接证明提交链路没有等待 |

公开[解析器](../../tools/analyze_ui_trace.py)与[合成测试](../../CodeTests/ui-response/README.md)可计算这些指标；本次重读保存的 20 秒轨迹与上述摘要一致。触摸时间戳、uptime、Weston 日志属于不同钟域，工具刻意不进行事件到帧的因果关联。

## 静态链路与原厂时序

运行时主屏模式核对为 1024×768、refresh=60000 mHz。定制 Weston 2.0 的 eagle-backend 中，EagleOutput::vsyncWorker 在 waitForVsync 后计算提交相位：

```text
floor(0.8 * floor(1000000000 / refresh_mHz)) - 1000 微秒
```

60 Hz 对应约 12332 微秒。离线指令与运行时模式分别核对；该值是同步后的计划提交相位，不能简单当作额外输入延迟相加，更不是实测触摸到发光时间。运行时 repaint_msec 为 5。

原厂 QML 的菜单滑动结束吸附为 200 ms，边缘回弹为 250+100 ms，部分弹窗延迟关闭为 300 ms；这些解释松手后的收尾，不能直接解释手指持续移动时的落后。控制屏拖动存在启动阈值与捕获异常规避逻辑，逻辑存在不代表本机正在触发异常。PageListView 的保存防抖为 200 ms，但未找到其直接实例，不能泛化为全部参数操作的等待。厂商 QML 和编译单元未分发。

## 三轮试验与恢复

每轮均为授权下的临时进程或 RAM 试验，设置约三分钟独立恢复监督；没有刷写固件或改写 system/vendor 分区。公开内容为试验设计、脱敏结果与源码组件，不含私有部署、内存写入器和厂商候选单元。

| 试验 | 假设与临时改变 | 验证结果 | 决策 |
| --- | --- | --- | --- |
| 1：Qt 渲染循环 | threaded 对照 QSG_RENDER_LOOP=basic，测试线程同步是否贡献主观迟滞 | 用户“和原厂差不多”；没有端到端测量 | 恢复原厂启动方式 |
| 2：Weston 重绘窗口 | repaint_msec 从 5 改为 8，尝试调整提交时机 | 最初“感觉会跟手一点？我也不好说啊”；切回对比“来回比较仍分不出来” | 恢复 5，不宣称提速 |
| 3：同步拖动 | HblListView 候选增加 synchronousDrag=true，尝试消除启动拖动时的坐标差 | 桌面特定触摸夹具：手指 140 px，原组件内容移动 100 px，候选 140 px；原厂嵌套页面离线入口检查通过。实机用户“仍然差不多”，并出现 MainScreen ReferenceError | 撤回，禁用同一候选，确切错误原因未确定 |

Qt 的 [synchronousDrag 文档](https://doc.qt.io/qt-6/qml-qtquick-flickable.html#synchronousDrag-prop)解释它对拖动开始时阈值位移的处理；这是行为语义参考。表中的 Qt 6.4.1 离线夹具结果不是相机实测 40 px 固定延迟，也没有测量屏幕扫描或呈现时间。候选在桌面加载成功不能保证原厂 AOT/cache 元数据及运行时兼容，因此本次没有重新发布该编译单元或把失败候选作为通用修复。

第三轮最终复核：原厂 GUI 与 Weston 正常运行，GUI nice=-15，repaint_msec=5；原厂 GUI 与 init 配置哈希未变，USB 配置回到原状态；实验映射与监督任务退出，临时 UI 试验文件清理；新日志正常，不再出现该 ReferenceError，GPU 错误为 0。用户此前也确认退出故障恢复到正常界面。恢复验收局限于本次运行，没有据此宣称长期稳定或冷启动验收。

## 宠物与原厂延迟的区别

宠物引擎/IPC 会增加工作量；最初手动启动 GUI 可能没有继承原厂 nice=-15，这只是影响假设，尚无完整宠物开/关对照。本轮原厂采样确认无宠物及 nice=-15，故不能把全部原厂迟滞归因于宠物。

宠物的优化是让 QML 在拖动输入事件中直接设置视觉坐标，绕过等待下次原生状态往返；透明像素通过 alpha 掩码让底层继续响应。用户确认改善的是该角色交互，屏幕实际拖动 FPS 与端到端延迟仍未独立测量。最初 Exit 结束宿主 GUI 导致 Logo 停留的问题及退出标记修正见[宠物模块](../../shimeji-overlay/README.md)。

## 仍缺的证据

下一项研究需要把同一输入的 Qt 接收、场景更新、缓冲提交和实际屏幕呈现时间对齐；高速录像可提供外部触摸到发光对照。测试应固定菜单、速度、原厂进程优先级与宠物开关状态，并做多轮隐藏顺序对照。当前接口平均值、显示相位静态公式与主观相似反馈都不足以确定优化参数。本次开源整理没有再次连接或修改相机。
