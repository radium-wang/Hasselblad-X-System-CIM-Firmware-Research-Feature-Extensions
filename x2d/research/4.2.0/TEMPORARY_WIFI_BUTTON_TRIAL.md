# Wi-Fi 页面空按钮：2026-09-15 上机结果

用户本轮要求在第一代 X2D 的 Wi-Fi 页面下方加入一个点击不执行操作的按钮，并明确相机已连接。此次按临时副本验证，没有安装到系统分区。

**USB 上传与文件校验通过；临时界面程序被 SELinux 拒绝执行，按钮未显示。** 本次没有停止或替换原厂界面。用户随后报告相机待机，此后没有继续发送设备请求；待机不是本次已记录的执行拒绝原因。

|---|---|
| 当前 USB 固件与运行状态 | 通过 4.2.0 和运行状态检查 |
| 原厂 camera-gui | 与固定分析输入的 SHA-256 一致 |
| 页面改动 | Wi-Fi 页 footer；点击处理为空；其他页隐藏 |

| 系统分区 | 只读；没有永久文件修改、安全策略修改或整机重启 |

候选数据仍在本次临时内存目录；没有候选进程运行。USB 句柄均由传输工具的 finally 分支关闭。不能因暂存成功就提示用户重启验收：本次没有建立持久启动入口，重启也不能让按钮出现。

## 拒绝依据

临时程序具有正常的可执行文件权限，独立 tmpfs 挂载也没有 `noexec` 标志。内核审计明确显示：来源域 `hbl_camera_service` 对目标类型 `hbl_camera_service_tmpfs` 的文件 `execute` 被拒绝，`permissive=0`。因此不是普通 chmod、文件传输不完整或按钮代码引起的启动失败。

离线复核官方 4.2.0 的 `/etc/selinux/vendor_sepolicy.cil`，SHA-256 为 `0c0e92e7aea517d981d8d1728b0612e1aada7e49812d77a5a97e06a98e328c50`：该域对自己的临时文件有读写、映射等权限，相关规则没有执行权限；对系统程序另有执行许可。这解释了本次临时目录路线的拒绝，不证明所有可能的受支持加载方式都不存在。

此前另一轮 bind-mount 替换失败记录与本次直接执行拒绝是两个独立结果；本轮没有重跑旧的界面停启或 bind-mount 安装脚本。没有关闭 SELinux、改变安全标签、修改访问策略或转用升级服务的权限。

继续实现 Wi-Fi 页内按钮，需要先找到原厂允许的自定义界面加载路径，或另行提出具体且可审查的系统改动方案。本轮没有现成可用的后续执行方案，不能要求用户仅靠唤醒或重启来解决权限拒绝。
