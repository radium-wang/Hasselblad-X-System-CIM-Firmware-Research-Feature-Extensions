# X2D 100C 4.2.0 主屏 Logo 离线替换与短时实机验证

## 适用范围与目标

仅针对第一代 X2D 100C 官方 4.2.0。用户提供黑底白色 `Nikon` 字标，希望替换开机时肩屏、主屏依次显示的品牌 Logo。已完成主屏显示后端的离线替换候选、回读预览和一次**不刷机的短时实机显示实验**。肩屏仍需解析 `exMCU_x2.cont` 的 Qt for MCUs 图像资源；本次没有修改 exMCU、系统分区或制作签名升级包。

## 验证

1. 用原厂主屏 H 图输入替换工具，输出 ELF 的 SHA-256 与原厂完全相同，20,736 个索引字节零变化。
2. 用只改左上角一个像素的测试图输入，输出 ELF 仅在文件偏移 `0x163D89` 改变一个字节（索引 `0` → `16`）。
3. 用用户图生成候选后，逐字节核对原厂与候选：差异全部位于文件偏移 `0x163D89` 至 `0x168E89` 的 Logo 数据区；从候选 ELF 独立回读生成的 PNG 与量化预览完全相同。

## 2026-09-27 主屏运行内存实验

用户授权先在已连接的相机上做主屏、不刷机实验，并在实验后确认短暂显示的是 **Nikon Logo**。以下区分设备读回与用户肉眼观察：

| 阶段 | 实机证据 |
| --- | --- |
| 前置核对 | 设备 `ro.product.device=eagle2_ec1706_native`、构建号 `24849`；本次启动槽 `ro.boot.slot_suffix=2`；运行中 `/system/lib64/weston/eagle-backend.so` 的 SHA-256 与本地 4.2.0 原厂文件一致。此前记录的启动槽是 1；本次只记录现状，不推断槽变更原因。 |
| 内存定位 | Weston 进程映射该原厂 ELF；读取对齐后的 Logo 区块（文件偏移 `0x163D00` 至 `0x168F00`，20,992 字节），SHA-256 为 `dfd277d4ef91d98e14bcd4287da47ce06c7ed3ea7f68bec0d9f4bfafa530d384`，与本地原厂区块一致。 |
| 临时替换 | 将原厂及 Nikon 对齐区块通过现有工厂 USB 入口暂存于设备 `/tmp` 的 tmpfs；逐个校验哈希。只向运行中 Weston 进程的对应私有内存映射写入 Nikon 区块，回读 SHA-256 为 `3d1078d038f5fe558aebb25e876546275e803791d43ce573f5f18b5045443459`，与本地候选一致。设置独立的 18 秒 GUI／内存恢复看门狗。 |
| 显示观察 | 暂停 `camera-gui` 约 4 秒，使 Weston 在无 GUI surface 时绘制 Logo；用户看到主屏显示 Nikon Logo。随后恢复 GUI。此项是用户现场观察，没有保存屏幕截图或视频。 |
| 回退核查 | 写回原厂区块后，Weston 内存 SHA-256 恢复为 `dfd277d4...a530d384`；看门狗结束后独立复核 `weston` 与 `camera-gui` 均为 `running`，原厂 ELF 磁盘哈希不变，`/system` 保持 `ro`，专用 `/tmp` 暂存目录不存在，USB 模式回到原先的 `rndis,mass_storage,bulk,acm`。 |

此次实机结果证明：**当前 4.2.0 运行中的 Weston 在 GUI 暂停时能从被临时替换的内存数据绘制用户提供的 Nikon 主屏 Logo。** 它尚未验证真正断电、再次开机时的主屏首次 Logo：内存修改随进程退出或重启消失，而首次冷启动发生在临时载荷能够从 USB 注入之前。原厂 OTA 校验／签名链仍未解决，离线 ELF 候选不能当作可刷固件。主屏候选也不能替换肩屏的 exMCU 资源；[exMCU 恢复边界](EXMCU-BOOT-AND-RECOVERY.md)单独记录。

## 主屏图像尺寸边界

用户实机观察到 162×128 的 Nikon Logo 偏小。再次检查 4.2.0 `eagle-backend.so` 的 AArch64 绘制分支：标准版路径在代码中固定宽 `0xA2=162`、高 `0x80=128`，逐像素按原图尺寸 1:1 拷贝并居中；它不按输入 PNG 的原始分辨率自动缩放。因此，**只替换标准版的图像索引字节时，最大且唯一的画布尺寸就是 162×128**。

同一函数还包含 Earth Explorer 专版路径，固定宽 `0x23A=570`、高 `0x1AA=426`，使用独立调色板和独立像素数组。这证明原厂已有更大图像的绘制路径；普通 X2D 100C 要显示自定义 570×426 图，仍需另行修改分支选择或数据指针，不能把 570×426 的 PNG 直接喂给当前标准版替换工具。此方案尚未离线生成或实机验证。

系统自带显示测试配置出现 `1024×768`；哈苏官方规格写主屏为 2.36-million-dot，换算为 24-bit RGB 时与 `1024×768` 像素一致。这两项支持主屏物理像素边界约为 1024×768 的判断，但尚未从本机当前 Weston 输出模式直接读回，不能将其写成已实机确认的最大 Logo 资源尺寸。要接近满屏，须改变渲染逻辑和图像存储布局；当前绘制循环没有为超出 framebuffer 的尺寸提供已验证的安全裁剪，不能仅修改宽高常量。官方规格：[X2D 100C datasheet](https://cdn.hasselblad.com/f/77891/x/38effba8fe/x2d_100c_datasheet_en.pdf)。

## 2026-09-27 250×250 彩色图短时实机实验

用户另提供黄色背景、白色斜纹和黑色 Nikon 字样的 PNG，源文件实际为 1254×1254，SHA-256 `2426263706af0f8089ff0bf91cb410cdfecf8228966905acc58ba8e1be0bff64`；按用户指定在主屏以 250×250 显示。原厂灰度 Logo 循环把同一字节写到 RGB 三个通道，不能仅替换图像数据来保留黄色。以下所有修改均只对运行中的 Weston 进程内存生效：

1. 在电脑上将输入采样到 250×250，编码为 256 色调色板加 62,500 个索引字节；量化预览的平均 RGB 通道绝对误差为 0.318/255。从生成的 ELF 候选独立还原该调色板和索引，得到与预览逐字节相同的图像。
2. 只在内存中把标准版绘制分支的宽、高常量设为 250，数据指针指向原厂专版图片数组内足够容纳的区域；把灰度查表和三次单字节写入改为 32-bit 调色板查表及一次像素写入。离线反汇编核对全部新指令，候选文件差异只在预期的代码与图片数据区。此候选文件不用于设备磁盘或固件升级。
3. 运行前确认本机仍为 `eagle2_ec1706_native`、构建号 `24849`、原厂后端 SHA-256 `a0ac02a5...b7f6217`；Weston 和 GUI 正常。将原厂代码和专版图片区域从 Weston 内存备份到 `/tmp` tmpfs，并逐块核对；候选载荷也暂存于 tmpfs，设置独立看门狗，在测试结束后恢复 GUI、原厂代码和数据。
4. 首次实机显示大小正确，但用户反馈黄色变蓝／青色、黑字仍黑。查明是红蓝通道的字节顺序与 framebuffer 相反；仅交换 256 项调色板中红蓝字节，代码和索引保持不变。修正后再试，并按用户请求重放一次，停留约 12 秒；用户确认 **250×250 大小正确、黄色背景及黑色 Nikon 字样正确，并已拍到照片**。本仓库没有保存该实机照片。
5. 最终独立只读复核：原厂代码区块和图片数据区块的 Weston 内存哈希均恢复，磁盘上的 `eagle-backend.so` 哈希仍为原厂值，`weston` 与 `camera-gui` 均为 `running`，`/system` 保持 `ro`，专用 `/tmp` 暂存目录不存在，USB 模式仍为 `rndis,mass_storage,bulk,acm`。全程未写系统分区、未刷机、未修改 exMCU。

此结果验证当前固件的主屏 **运行内存短时显示路径** 可绘制用户提供的 250×250 彩色图，且可回退原厂状态。它不证明完整冷启动时会显示此图，也不代表已有可持续安装的方案。彩色预览与离线候选留在被 Git 忽略的 `x2d/outputs/startup-logo-4.2.0/`；没有把设备端工厂 USB 命令或部署脚本放入公开仓库。
