# 原厂主菜单第十二格“耍起功能”入口：可行性核对

对象：第一代 X2D 100C 官方 4.2.0。本文为静态证据和候选设计，不是已安装功能。

`camera-gui` SHA-256：`16391452abdc69de9e0807e065c0f4ab3f1ccb5fc288f6fc4e6f5cb3bdca12e0`。

## 目标

保留原厂 MainScreen、原厂十一项、触控和按键导航。在通常三行四列布局的最后一格增加“耍起功能”和烧瓶 SVG，打开无副作用测试页。页面默认隐藏、可预创建，按英文 `EXIT` 返回原厂主菜单。

## 本轮新增的静态证据

从固定固件的内嵌资源重新读取 MainScreen.qml、MainMenu.qml 和 MainMenuViewModel.qml：

1. MainMenuViewModel 将 favoriteModel 定义为可写的 var 属性，默认引用 FavoriteModel 单例。不是 readonly 属性。这提供了适配模型的候选接入点，不必直接修改原厂 C++ 单例的内存结构。
2. MainScreen 网格的 model 绑定到 viewModel.favoriteModel。非稀疏模式四列、三行；布局、原厂 FramedImage delegate、触摸与按键处理已存在。
3. 网格除了读取 label、labelContext、iconSrc、itemEnabled、menuName 等角色，还会调用 model.itemEnabled(ix) 判断导航可选性。简单换成仅含数据的 QML ListModel 并不保持完整接口。
4. 点击发出 loadSubMenuItem；MainMenu 会把名称交给 SubMenu.menuFile。未知名称无法自动变成自定义页面，必须有明确的扩展分支。
5. MainMenuViewModel 的 inMenu 绑定到原厂子页面加载器 active。独立常驻容器仅改变 visible 不会自动进入原厂子页状态，需要同步焦点、菜单状态和退出处理。
6. 原厂返回路径会清空 Loader 来源。因此“耍起功能”页与该销毁路径分开管理，同时保留退出菜单时的清理语义。

## 推荐实现候选

### 保留原厂网格，扩展其模型

构造一个与原厂模型接口兼容的适配层：原厂项目顺序、角色、动态可用性和变更通知继续转发；末尾追加一个专用 `x2dPlayUi` 项目。它提供 itemEnabled(ix) 方法，并处理源模型 reset 和增删变化。

不能预设所有状态永远恰好十一项。第十二格方案应检查当前非稀疏布局与源项目数量；遇到不支持的布局或数量时拒绝追加，不能覆盖原厂条目。

该适配层可以由启动模块提供，再在原厂页面创建期间将 favoriteModel 指向它；也可以通过经过验证的编译菜单单元实现相应绑定。可写属性只是静态可行性依据，尚未验证实际对象获取、赋值时机、元对象接口和 ABI。

### 在原厂菜单树里接入自定义页面

原厂十一项继续走原路由。新增项目在交给原厂 menuFile 查表之前，由扩展路由识别并打开常驻“耍起功能”容器。

需要接通媒体忙状态、重复点击保护、原厂焦点、半按退出、菜单关闭和嵌套返回。不能将所有 closeMenu 调用改成显示自定义页面；也不能把独立页面隐藏与原厂菜单状态更新混为同一操作。

`ResidentPlayHost` 保持同一个 `PlayPage` 实例并处理返回；它不是任意程序启动器。

### 开机接入

对方 AF-C 实现可作为两份编译单元重定向的参照，但主菜单 C++ 数据模型与 AF-C 的 QML 对象列表不同，不能直接复制其新增对象逻辑。对方现有部署脚本也不能原样套用本机：活动系统分区不同，且本机已有同名的独立预览进程。

## 当前结论与验收

有明确实现路径，且可以保留原厂主菜单而不是重做整页；尚未形成可安装的第十二格版本。

离线阶段应先验证源模型角色与通知转发、十一项行为不变、扩展项导航可选、计数和布局条件、路由及页面生命周期。设备阶段再验证正常启动、反复进出、返回与半按退出、休眠恢复、失败回退以及真实冷启动时间。

不能仅凭沿用原厂网格就承诺与原厂完全相同的耗时；扩展初始化仍可能增加开机成本。本轮只读取资源与配置并整理结论，没有新增机内菜单、安装 AF-C 或修改启动配置。
