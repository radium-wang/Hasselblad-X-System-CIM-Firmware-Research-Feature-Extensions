# macOS：X2D 4.2.0／55V RAM 对焦速度实验

## 状态与边界

`x2d_af_speed_mac.py` 将同目录 Windows 实验的主机流程移植到 macOS：使用 `../x2d-afc-research/collect_x2d_af_usb.py` 已知的 PyUSB 工厂接口，并原样复用本目录的 `device_backend.sh` 与 `transaction.sh`。macOS **15 秒限时模式**曾完成一次实机激活、原函数恢复及独立 `status` 核验；新加的**手动恢复模式尚未上机验证**。Windows 旧实机记录不是新模式的验收。

仅适用第一代 X2D 100C、原厂 4.2.0、XCD 55V（产品 ID 81470）。它只在本次 `camera-service` 进程 RAM 中替换完整函数；不会写入机身分区或镜头固件。速度命令的数值限幅不是电流、温度或机械安全认证，实际运动速度及损伤风险未测量。**不要在不接受该风险时运行安装命令。**

`run` 是旧的 15–60 秒设备端自动恢复模式。`install-manual` **没有倒计时、没有自动撤回**；补丁保持到显式 `restore`、`camera-service` 重启或相机完整重启。拔掉 USB 不会撤回；如果恢复无法核验，切勿重复安装。恢复写入失败时服务可能停在 `STOP`，需先看状态；完全断电重启可清除该 RAM 补丁，但不等于证明实验中镜头未受损。手动模式运行期间不要更换镜头。

## 文件与依赖

从本目录执行下列命令。需要 macOS、Python 3.9 或更新版本、Apple Clang、PyUSB、libusb，以及 `standalone_handoff/requirements.txt` 的离线 ELF 依赖。构建输入为从官方 X2D 4.2.0 `system.img` 提取的 `system` 根目录，其 `lib64/libaaa.so` 必须匹配脚本固定 SHA-256。USB 固定为 2756:0009、interface 3 alt 0、OUT 0x04、IN 0x85；既有 macOS 客户端支持的机身环境仍需实机核对。

```sh
python3 -m venv ../../../../.venv-x2d-af-speed
source ../../../../.venv-x2d-af-speed/bin/activate
python -m pip install -r standalone_handoff/requirements.txt -r ../x2d-afc-research/requirements-usb.txt
brew install libusb
python -B x2d_af_speed_mac.py self-test
python -B -m unittest test_af_speed_mac.py
python -B x2d_af_speed_mac.py build --system-root '/path/to/x2d-system-root'
```

`build` 从原厂 ELF 读取 1068 字节原函数，编译 `fastscan.S`，核对原函数和最终候选函数的精确 SHA-256；生成物留在 `outputs/mac-af-speed/artifacts/`，本地状态留在 `outputs/mac-af-speed/`，该目录有 `.gitignore`。不要将函数二进制、设备状态文件或旧的 `prepared-*.sh` 上传仓库。此 Mac 构建**没有重新完成 1402 组 Unicorn 模拟**：本轮 `unicorn 2.1.4` 在 macOS 运行时 `mem_map` 触发 `SIGILL`，因此没有把模拟结果虚报为通过；旧资料中的模拟结果仍是历史证据。

## 只读预检、手动安装与恢复

```sh
python -B x2d_af_speed_mac.py --timeout-ms 4000 preflight
```

仅当其确认 4.2.0、55V、原函数哈希和条件加速数值后，用户在现场且明确接受未测的镜头风险时，才使用新的无倒计时入口。它不附加 `strace`，不会写入机身／镜头固件，但必须由你明确执行恢复。

```sh
python -B x2d_af_speed_mac.py --timeout-ms 4000 install-manual --user-present --accept-unmeasured-lens-risk --acknowledge-no-timer
python -B x2d_af_speed_mac.py --timeout-ms 4000 status
python -B x2d_af_speed_mac.py --timeout-ms 4000 restore
python -B x2d_af_speed_mac.py --timeout-ms 4000 status
```

安装成功应显示 `MANUAL_ACTIVE`；只读 `status` 应显示 `mode=manual state=CANDIDATE_ACTIVE`。`restore` 仅接受同次进程的完整候选哈希，恢复后要求显示 `RESTORED_AND_VERIFIED`；再次 `status` 应显示 `mode=manual state=ORIGINAL_VERIFIED`。**不要对未知／部分字节再次安装或盲目重试恢复。**

需要以往的限时模式时，`run --seconds 15 --user-present --accept-unmeasured-lens-risk` 仍存在；它会自动恢复，不是手动模式。

对经单独授权的后续限时测速，可加 `--capture-af-log`。此选项在设备私有 `/tmp/afw-.../af.log` 启动 `seconds+20` 秒的有界 `logcat`，仅保留 `StateSequenceAF` 进入与 `StateAfSingle::handleAfResult` 事件；先确认记录器已创建，再派发 RAM 事务。原厂函数恢复核验后等待记录器设备端超时，把最多 4096 字符的 AF 事件及按设备窗口筛选的配对结果存入本地 `outputs/mac-af-speed/plan.json`，随后清理私有目录。设备断线不取消记录器的本地超时；采集失败不应混同于恢复失败。记录器**单独在原厂 AF-S 下完成设备演练**，但与 RAM 候选联用仍只通过离线测试；不得把它写成现有样本的补充计时。

若安装过程 USB 回应丢失，只运行只读 `status`，不要重新发安装命令。若读到同次进程的完整候选、且设备安装事务已退出，才使用上面的 `restore`。恢复命令自身回应不确定时，不会自动重试；先看 `status`，必要时完整断电重启。

恢复入口拒绝未知字节、旧进程、没有计划文件和不确定的二次写入。不能通过 USB 核验时，停止尝试并完整断电重启；不要使用旧地址或另一固件版本的恢复脚本。`status` 对当前进程显示 `ORIGINAL_VERIFIED`、`CANDIDATE_ACTIVE`、`PROCESS_RESTARTED` 或 `UNKNOWN_BYTES`，但不会代替镜头物理安全检查。

## 本轮验证记录

- macOS Python 3.9：静态构建和完整原厂／候选 SHA-256 核对通过；生成 `candidate.json` 与独立交接包内容一致。
- macOS：PyUSB 帧格式自测通过；12 个主机单元测试通过，覆盖 13 个限时事务场景及手动事务故障分支，并模拟无倒计时安装、手动恢复与 USB 回应丢失。
- 实机：`preflight`、一次 15 秒 `run`、自动恢复及独立 `status=ORIGINAL_VERIFIED` 已完成。
- **未执行**：新加的 `install-manual`、其配套 `restore`；也未测电流、温升、运动速度或合焦时间。

同日，在用户明确同意未测镜头风险、现场监护且确认 55V、AF-S、实时取景正常后，用修订后的后端执行**一次** `run --seconds 15`。设备报告 `TEMPORARILY_ACTIVE`，到期后主机核验完整原函数哈希及 camera-service 线程状态，输出 `ORIGINAL_VERIFIED`；随后独立只读 `status` 仍为 `mode=timed state=ORIGINAL_VERIFIED`。用户在窗口提示后半按一次，机身报告合焦且无可见异常。无系统分区或镜头固件写入。

原厂对照日志仅保留一组完整 AF 状态机事件：`1790375694.835` 进入、`1790375695.202` 成功，约 367 ms。试验后仅保留一组事件：`1790375853.783` 进入、`1790375854.055` 成功，约 272 ms。事务没有保存精确的设备端 ACTIVE／RESTORED 时间戳，后一组事件靠近恢复核验，因此**无法确认半按发生在候选代码生效期间**；两次目标距离／初始镜片位置也没有严格配对。这组数字不能证明候选带来 95 ms 或约 26% 提速，更不能证明机械安全。此次结果只支持：RAM 候选可被限时激活、自动恢复且机身一次半按后功能正常。候选是独立的 55V 扫描命令修改，未移植 X2D II 识别／AF-C 算法，也不调用激光雷达。

为避免下次重现“无法确定半按是否在候选窗口”的歧义，已离线修改事务脚本，增加设备时钟的纳秒格式 `ACTIVE_AT`／`RESTORED_AT` 记录，并在清理临时日志前保存到本地计划文件；13 个主机单元测试和 USB／shell 自测通过。**此时间戳修订是在本次实机测试后作出的，尚未再次上机验证；不能把它回填到本次记录。**

时间戳修订随后在用户另行同意的第二次 15 秒限时试验中实机运行：`ACTIVE_AT=1790376519.646588401`、`RESTORED_AT=1790376534.961719909`，到期后完整原函数哈希、线程状态及独立只读 `status` 均为原厂。测试前同一组远／近目标原厂 AF-S 分别为 294 ms（`1790376436.046→6436.340`）和 326 ms（`1790376439.047→6439.373`），用户又使镜头回到远处并确认合焦。提示发出后用户半按两次且机身均无异常，但日志记录的开始时间为 `1790376542.636` 与 `1790376545.228`，分别比恢复时刻晚约 7.67 与 10.27 秒，对应合焦 404 与 395 ms。**两次都发生在原厂代码下；本轮仍没有候选生效期间的 AF-S 样本。** 这反映出消息传达／人工操作总延迟超出 15 秒窗口，而非候选速度结论。不得把这两组 404／395 ms 记为候选数据或据此评判补丁。

用户又单独同意一次最长 45 秒、只半按一次的限时试验。设备记录 `ACTIVE_AT=1790376695.874628218`、`RESTORED_AT=1790376741.131021961`；唯一 AF-S 事件 `1790376706.593→1790376706.840`，约 **247 ms**，确实完整落在候选窗口内，服务报告 `Success`。用户确认只按一次、同一近处目标、合焦且机身无异常；脚本和独立 `status` 再次核验原厂函数已恢复。该次日志含 `SetFocusScan,pos:32767,speed:2595` 与最终绝对位置到位，说明是混合路径，**不能仅由总时间断定改过的选速分支实际贡献多少**。

恢复原厂后用户按相同远处→近处目标再做两次 AF-S，均合焦；近处事件 `1790376869.660→1790376870.023` 约 **363 ms**。然而设备日志显示候选近处从 `cur_pos=112` 到最终 `1100`，原厂近处从 `114` 到最终 `1691`：行程分别约 988 与 1577 位置单位，后者明显更长。用户随后确认机身为手持或构图有变化，AF 点／目标平面并未严格固定。原厂近处还记录多次扫描命令速度 5190／2595／1297，而候选可见的一次为 2595；命令上下文未配对，不能据此求倍率。焦点位置差异和构图变化使 247 对 326／363 ms 的比较**不可归因于速度补丁**。仍需固定机位、固定 AF 点及目标平面、相同起止镜头位置和多组成对样本，另外测过冲、温升与失败率；本记录不是性能或机械安全验收。

用户再次请求测试后，先固定相机与 AF 框，将近处高对比卡片在同一位置移入／移出视野；候选写入前的两组原厂远→近对照，近处合焦分别约 **333 ms**（`1790377723.617→7723.950`）和 **342 ms**（`1790377767.308→7767.650`），终点分别为 **1011／1012**，远处终点为 **134／143**。这比手持样本可比性更好。此前另一次原厂近处测试虽合焦，但连续多帧 `target_pos=0`、置信度 0；故未用作固定目标对照。

经用户确认镜头回到远处，再按同一授权边界进行一次 45 秒、仅一次半按的候选窗口。`ACTIVE_AT=1790377841.936718660`、`RESTORED_AT=1790377887.195027247`；窗口内 `1790377852.401` 报 AF-S `Success`，最终镜头位置 **1010**，与两组原厂的 1011／1012 匹配。用户确认一次半按、合焦且无可见异常；完整原函数哈希与独立 `status` 再次为 `ORIGINAL_VERIFIED`。但设备主 `logcat` 环形缓冲区在读取前冲掉了该次 `FindFocusStart`，`system`／`all` 缓冲区也未找回，因此**没有可验证的候选总合焦时间，不能计算提速**。仅能确认同目标、同终点条件下候选仍可合焦。后续若获新授权，必须先在设备 `/tmp` 使用有界、限时的 `logcat -f` 采集 AF 起止事件；本版设备帮助列出 `-f`、`-r`、`-n`，但尚未验证实际采集事务，不应再依赖事后环形缓冲区。

为此加入可选 `--capture-af-log` 后，15 项主机单元测试及 USB／shell 自测通过。用户同意的一次**无 AF 代码写入**设备端记录演练，使用设备本地 50 秒超时与私有 `/tmp` 文件，成功保存两组完整 `FindFocusStart → Success` 事件（472 ms、380 ms），另有一条采集边界前的孤立成功事件；因此离线配对器会忽略没有开始时间的结果，并只把开始与成功都落在候选 `ACTIVE_AT`／`RESTORED_AT` 之间的配对标为有效。演练脚本退出并清理临时目录。此结果验证独立日志采集，不是 AF 提速效果，也不追溯填充上面缺失的 `FindFocusStart`。`--capture-af-log` 与 RAM 候选的组合尚未上机。

随后用户单独同意一次固定机位、同一近卡、仅一次半按的**45 秒 RAM 候选＋有界日志**组合试验。试验前又取得一组原厂近处 `1790378600.241→8600.713`，约 472 ms、终点 1010；另外两组固定目标原厂近处为 333／342 ms、终点 1011／1012。远处重新合焦后派发，设备记录 `ACTIVE_AT=1790378684.799090406`、`RESTORED_AT=1790378730.070276077`，记录器完整保存唯一配对 `1790378697.284→8697.580`，`Success`，**296 ms**，完整落在候选窗口内。候选 PDAF 起点约 108、终点 1008；用户确认一次半按、合焦、取景与镜头动作无异常。完整原函数哈希和随后独立只读 `status` 都为 `ORIGINAL_VERIFIED`，临时日志目录已清理。

恢复原厂后再做一组同目标远→近对照：近处 `1790378850.762→8851.113`，**351 ms**，远处终点 94、近处终点 1011。候选的扫描命令为 `SetFocusScan,pos:32767,speed:2595`；恢复原厂后同方向的可见扫描命令为 `speed:1297`，约 2.001 倍，与候选在该扫描档的 ×2 设计一致。候选首次可见扫描命令至最终到位约 183 ms，原厂后测约 250 ms，但这段仍包含其他镜头控制及收尾，不能解释为纯机械速度。四个固定目标原厂近处总时间 333、342、472、351 ms，中位数 346.5 ms；唯一完整候选样本 296 ms，相对这四个样本的中位数低约 14.6%。**这只是小样本、非随机化的初步信号**：不能证明重复性、失败率、温升或镜头机械安全，也不能证明 X2D II 算法已移植。后续需控制镜头起点和目标平面，采集多组交替样本；任何进一步 RAM 写入都需新的实机授权。
